- Crear rama: `git checkout -b feat/<ticket>-<short>` desde `develop`.
- Invocar `implementer` para la tarea (dry-run → luego generar cambios tras aprobación).
- Revisar la propuesta localmente; pedir al `reviewer` revisar el diff.
- Resolver issues detectados por `reviewer` (humano), actualizar rama.
- Commit atómico con mensaje siguiendo convenciones.
- Abrir PR hacia `develop` y pedir revisión final.

3. Reglas:
- Una tarea = una rama = un commit atómico (no mezclar responsabilidades).
- Si `implementer` se atasca dos veces: documentar el bloqueo en `CONTEXT.md` y proceder con edición manual por un developer.

4. Releases y hotfixes:
- Cuando se quiera desplegar a producción, crear rama `release/X.Y` desde `develop` para pruebas finales y despliegue a Vercel.
- Para errores críticos en producción, usar `hotfix/` desde `main` y seguir flujo de merge a `develop` y `main`.

5. Comandos útiles (ejemplos):
